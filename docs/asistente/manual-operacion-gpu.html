1. Propósito, alcance y estado

Este manual describe el paquete preparado para un futuro host GPU dedicado dentro de la UE. Se limita a inferencia local mediante vLLM, FastAPI para embeddings, reranking opcional y redacción, Redis opcional, Langfuse local opcional y Caddy como único borde. No crea servidores, no descarga pesos en el host, no usa APIs externas de IA ni activa producción.

Principio de operación: los pesos, ruedas e imágenes se revisan en una estación de preparación separada; el host final recibe un soporte cifrado y sólo ejecuta docker load, comprobación de hashes y arranque controlado.

El estado actual es NO APTO PARA PRODUCCIÓN. El sandbox ha demostrado sólo una prueba parcial de red Docker con una sonda CPU ligera. No existe evidencia de GPU, vLLM, Caddy, mTLS, firewall de host, backup/restauración ni latencia con modelo real.

DDL, datos UE y rollback

Este paquete no ejecuta DDL ni accede a staging o producción. Cualquier cambio de esquema es aditivo, pertenece al equipo de captación y se ensaya sólo en la base local vacía asignada. No se permiten DROP, TRUNCATE, DELETE masivo, prisma migrate deploy, db push ni extensiones desde este alcance.

Los datos no llegan al host GPU hasta aprobar contrato de encargado, región efectiva UE, subencargados y conectividad privada. El borde usa TLS con mTLS; los discos, volúmenes y copias requieren cifrado documentado. El rollback apaga tráfico y generación, detiene la pila local y rota credenciales si procede; no borra tablas aditivas.

2. Arquitectura y aislamiento de red

La aplicación conserva permisos, filtros ACL y minimización. Un relay o VPN aprobado —pendiente— es el único origen que puede llegar a Caddy. Caddy exige mTLS y token de gateway, no usa ACME y descarta logs de solicitud. vLLM, FastAPI, Redis y Langfuse no publican puertos.

Aplicación autorizada ─ relay/VPN aprobado ─ mTLS + token ─ Caddy:443
                                                │
                    red Docker interna: internal=true, sin puertos
               vLLM · FastAPI RAG · Redis opcional · Langfuse opcional

Una red bridge ordinaria puede dar salida externa mediante enmascaramiento. Por ello interna declara internal: true y nftables del host añade denegación de salida. Ambos controles y la prueba negativa por namespace son obligatorios [4].

No sustituir controles: internal: true no acredita el aislamiento de Caddy, pues Caddy se une también a la red de borde. Firewall, CIDR exacto de relay y probar-sin-salida.sh son bloqueantes.

FastAPI y vLLM fuerzan modo offline y telemetría desactivada. vLLM reconoce VLLM_NO_USAGE_STATS=1 y VLLM_DO_NOT_TRACK=1 [5]. Los pesos se montan sólo lectura.

4. Preparación verificable del suministro offline

La estación de preparación separada ejecuta preparar-artefactos.sh. Exige digests completos de imágenes y revisiones inmutables de modelos, crea manifiestos y calcula SHA-256 sobre artefactos presentes.

  • Revisar licencia, revisión, tokenizer, formato y soporte vLLM.
  • Fijar imágenes por @sha256:, sin tags móviles.
  • Fijar modelos por commit de 40 hexadecimales y ruedas por SHA-256.
  • Revisar SBOM, vulnerabilidades y usuario no root de la imagen RAG.
  • Hacer revisión de dos personas antes de transferir por soporte cifrado.

5. Instalación controlada, arranque y pruebas

  1. Preinstalar por vía offline Docker/Compose, driver NVIDIA, nvidia-smi, nftables, rsync, Python, SHA-256 y age.
  2. Copiar .env.example a .env, completar secretos fuera de Git y aplicar permiso 600.
  3. Ejecutar instalar-offline.sh sin firewall para revisar hashes y Compose, sin arrancar servicios.
  4. Desde consola fuera de banda, aplicar nftables únicamente con CIDR de relay y SSH aprobados.
  5. Arrancar perfiles mínimos; ejecutar probar-sin-salida.sh, latencia y backup/restauración.
Resultado parcial existente: la sonda Docker CPU del 25/10/2026 no resolvió DNS externo ni conectó a 1.1.1.1:443. No valida GPU, Caddy, vLLM, FastAPI, mTLS, nftables ni backup.

6. Copias, restauración e incidente

backup.sh cifra copias locales con destinatarios públicos de age y SHA-256. restaurar.sh solicita confirmación y crea volúmenes nuevos sin sobrescribir el estado actual. Ambas operaciones requieren prueba real y recibos antes de activación.

Ante incidente: apagar tráfico y modo local, detener contenedores, rotar secretos y certificados cuando corresponda, y preservar evidencia mínima sin texto personal. No borrar tablas aditivas como rollback.

7. Checklist de paso controlado

  • Proveedor, región UE, DPA, subencargados, relay/VPN y responsables aprobados.
  • Consola fuera de banda y CIDR exactos disponibles.
  • Bundle revisado por dos personas, hashes correctos y sin marcadores.
  • Secretos distintos, permisos 600 y certificados locales restrictivos.
  • Firewall drop y prueba negativa por contenedor superados.
  • Sin puertos publicados salvo Caddy 443.
  • Backup/restauración, evaluación de 100 casos, ACL, inyección, TTFT y VRAM superados.
  • Aprobación jurídica de privacidad, consentimiento, RAT/ROPA, EIPD y Cookiebot.
  • Aprobación expresa de Víctor antes de activar.

8. Decisiones pendientes

Permanecen pendientes el host y contrato, relay/VPN, modelo/checkpoint/cuantización, responsables de operación y restauración, y validación legal. La programación efectiva del informe queda bloqueada: este paquete no instala scheduler y los cron continúan desactivados.
